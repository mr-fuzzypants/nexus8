# Part A — SR&ED Narrative

## A1. Project objective

The video-op pipeline (VOP project) now produces a genuine operation graph in the data layer: mask tracks (selection ops) feed generative ops (remove), whose outputs ingest as derived render assets with full `VersionLink` lineage to the exact source-video and mask-track versions consumed. The artist-facing surface, however, still presents a single-step model: one mask layer, one ephemeral removal overlay held in client memory (`videoRemovals` state — lost on reload), gated by one visibility toggle. The workflow the artist actually needs is graph-shaped: *mask an object → run an operation → view the result as its own track → possibly mask/operate on that result → possibly combine multiple mask tracks into one operation*.

The objective is to surface this DAG in an artist-legible form **without a node-graph editor**, testing the interaction thesis (established by survey of incumbent tools — DaVinci Resolve's serial-node color page vs. Fusion, Autodesk Smoke/Flame's timeline+BFX, Runway's generations-with-"use as input", Photoshop/AE's layer-stack-as-implicit-DAG) that:

1. **Results are durable child tracks** of the mask layer that produced them, restored across sessions from server-side lineage, each with **takes** (one per generation run) and a pinned selection.
2. **Chaining is implicit retargeting** — selecting a result track makes it the target of subsequent ops; no "wire an edge" concept.
3. **Combining is multi-select** — several mask tracks feeding one operation via dispatch-time union; no materialized combine node until evidence demands it.
4. An explicit graph rendering, if ever needed, is an **escape hatch view derived from the same lineage**, deferred until branching demand is observed.

No incumbent tool couples this: NLE/compositing packages have either the flat stack (no generative-op provenance) or the full node graph (artist-hostile for this audience); generative video tools (Runway) have takes and chaining but no frame-accurate annotation, no mask-track provenance, and no combining.

## A2. Technological uncertainties

### U1 — Whether a provenance DAG can be surfaced as a lineage-nested stack without losing legibility

The interaction thesis (stack-first, graph-never-by-default) is supported by tool-survey analogy, not evidence, and the analogies break in specific ways: Resolve's serial chain is *per-clip and linear*; Runway's chains are *linear and single-input*. This workflow has genuine branch points (one mask track feeding several ops; several mask tracks feeding one op; a result re-masked). It is unknown (a) at what graph complexity the nested-stack rendering stops answering the artist's core questions ("what made this?", "what will this op consume?") without a graph view; (b) whether *implicit* retargeting (ops silently target the selected result track) is legible or hazardous — the still-image pipeline's analog (ops target the active layer) has no depth, and a mis-targeted multi-minute GPU removal is an expensive misfire; and (c) how take-pinning on intermediate nodes propagates intent — if a downstream op consumed take v2 and the artist re-pins to v3, is the downstream result now stale, and how is that surfaced without a dependency-graph concept.

### U2 — Durable identity and take semantics for span-scoped derived results

Result tracks anchor to render assets keyed by CRDT layer ids, which VOP-F11 established are not durable identities (the mask-track restore protocol exists precisely because layers evaporate). Takes compound the problem in a way the still-image render grid never faced: two runs of the same result track may cover **different frame spans, at different resolutions, from different mask-track versions and different removal tiers** (VOP-F22/F23a: 41-frame VOID single-window vs. 197-frame chunked vs. native-res eraser runs, all on one layer). It is unknown whether run-as-take with a single pinned selection (the two-axis convention, INP-F13) is a sufficient version surface for span-divergent runs, or whether span divergence forces splitting into separate result tracks — and what the overlay/compare semantics are when the pinned take covers only part of the span the artist is scrubbing.

### U3 — Frame-accurate A/B comparison of span-scoped derived clips

Result review requires flicker-comparison (VOP A4 design; hold-to-compare shipped as hold-C) between a sub-span derived clip and the source, frame-locked during playback and scrubbing. Partially derisked: the dual-deck sync (hidden `<video>` element seek-followed against the transport with drift correction) works on the first real clips. Unknown at production scale: seek-latency behaviour at native-tier resolutions and on multi-take switching (decode cold-start per take), and whether span-edge behaviour (playhead crossing into/out of the result span mid-playback) reads as intentional or as a glitch.

### U4 — Chaining generative ops onto derived assets

The op envelope (VOP-U8) was validated with library video assets as the sole source type. A derived result is a different animal: a sub-span clip (frame 0 of the result = frame `span_start` of the source), possibly at reduced resolution (tier-bound VOID output) or native (composited), with provenance one edge deep. Unknown: (a) whether the staging pipeline (keyed by asset/version/tier/span) generalizes to render-asset sources without forking; (b) the frame-index and coordinate rebase contract — VOP-F9 established that multi-resolution prompt chains fail *silently as plausible-but-wrong results*, and chaining adds a span-offset axis to exactly that contract; (c) whether mask tracks on a derived asset (re-masking the result) round-trip through the track restore protocol whose index is keyed by video asset.

### U5 — Dispatch-time mask union across heterogeneous tracks

Combining tracks as a per-frame union composited at dispatch assumes the constituent tracks are commensurable. They need not be: different propagation spans (union at frame N when one track has no frame N), different staging tiers (854-wide vs. native masks), different confidence. Unknown: the correct resolution rules (missing-frame = empty vs. abort; resolution mismatch = upscale-nearest per VOP-F13's binary-preserving resize), and whether union interacts with the generous-mask prerequisite (VOP-F16/F21/F23a: dilation is a removal-quality prerequisite) — dilating before or after union produces different contact-boundary behaviour precisely where VOP-F16 found segmentation weakest.

## A3. Hypotheses

- **H1 (Durable result tracks on the render store):** The existing layer-render store (two-axis versioning, `selected` symlink, render-grid endpoint) is a sufficient durable substrate for video result tracks with takes — hydration is a client-side lineage walk requiring no new backend tables; span metadata per take (already recorded in `Version.data.generation`) drives the overlay.
- **H2 (Stack-first legibility):** The lineage-nested stack + implicit retarget covers the dominant workflows (single chain ≤3 deep, combine of ≤3 masks) without a graph view; provenance questions are answered by a per-track recipe rendering of `VersionLink` edges. A graph view becomes necessary only if observed sessions produce nodes with ≥2 parents *and* ≥2 children.
- **H3 (Run-as-take survives span divergence):** Span-divergent runs coexist as takes of one result track, with per-take span metadata and the overlay simply inactive outside the pinned take's span; splitting into separate tracks is unnecessary.
- **H4 (Dispatch-time union suffices):** Multi-mask removal needs no materialized combine entity — per-frame union at dispatch (empty-on-missing-frame, binary nearest resize to the staging tier, dilation after union) composes with all removal tiers unchanged.
- **H5 (Chaining rides the envelope):** Ops on derived assets require only (a) staging generalized to render-asset sources and (b) an explicit span/coordinate rebase contract (extending VOP-F9's); the dispatch/poll/ingest envelope and the SPA op surface are unchanged, per VOP-U8.

## A4. Work performed

**Interaction-architecture survey and design (August 8 2026).** Incumbent-tool survey (Resolve color/Fusion split, Smoke/Flame timeline+BFX, Runway generations, Photoshop/AE stack-as-DAG, Mocha/Silhouette roto layers, ComfyUI/Nuke as the graph-first counter-examples) conducted; stack-first thesis adopted (A1). Scope decisions recorded: milestone 1 = durable result tracks + takes + compare affordance; combine = dispatch-time union; chaining = implicit retarget; recipe card and graph view deferred behind observed need.

**Phase 1 implementation (August 8 2026).** Durable result tracks implemented per H1 — entirely client-side, confirming the hypothesis's "no new backend" premise at least at build time: hydration walks each restored mask-track layer's render grid (the existing `renders/?layer_id=` endpoint), filters `generation.op == 'remove'` runs, and rebuilds per-layer takes with span metadata from the run's persisted `generation` record (`span_start` + `frames_processed`, mirroring the dispatch-time overlay-span rule that guards against VACE window trimming). The session-only `videoRemovals` state was replaced by a pure derivation from result-track state (pinned take → overlay input), leaving the viewport overlay contract untouched. Panel result rows nest under their producing layer (connector + outline swatch in the layer colour + take selector `v{run} · {start}–{end}f · {tier}`), reusing the layer's `render_visible` toggle as the result's visibility (one source of truth). Take pinning rides the still-image `selected`-symlink endpoint; a freshly completed run auto-pins (recorded deviation from the still-image "later runs never move the selection" rule — the artist is watching the run land, and reload must restore what they saw). The hold-C flicker-compare (VOP A4) predated this work; Phase 1 adds only its discoverability affordance on the result row. **Pending live verification:** end-to-end reload-restore against the dev DB's existing removal runs (older runs' generation records predate some fields — the hydration path tolerates missing `span_start`/`frames_processed` but the fallbacks are untested on real rows).

- **F1 — first-session legibility failure of the bare result row: a span-scoped overlay with no spatial index is invisible by default (U1/U3 evidence, August 8 2026).** First artist contact with the Phase 1 rows produced "I see the derived layers but it's unclear what I'm looking at and how to see results or do A/B." Diagnosis: the result overlay renders only when three conditions coincide (mask mode + playhead inside the take's span + `render_visible` on), and nothing in the UI indicated *where* the span was — the span numbers lived only in the take label, requiring a blind scrub; the flicker-compare existed but was keyboard-only (hold C) with its sole affordance a tooltip. Three discoverability mechanisms added in response: (a) **click-to-seek** — clicking a result row selects the layer *and* jumps the playhead to the pinned take's span start, making the result visible in one gesture; (b) **result-span timeline bar** — a thin emerald strip along the lane bottom (distinct from the centered cyan propagated bar) shows where each layer's pinned take lives; (c) **on-screen press-and-hold compare button** over the viewport (same mechanism as hold-C), shown whenever a visible result exists. The finding worth recording for U1: *derived tracks need a spatial index before they need provenance detail* — the artist's first question was "where is it," not "what made it," which reorders the Phase 4 recipe-card priority below span visibility.

- **F2 — the mask needed node status before chaining did: artist feedback identified the 1:1 layer↔track coupling (with GPU-only authoring and an invisible version lineage) as the surface's binding constraint; resolved by promoting the mask track to a first-class take-bearing node with a no-GPU authoring path (August 8 2026).** After first contact with the Phase 1 result rows, the artist's structural request was: create a layer → author a mask track *by hand* (no Modal job); a SAM2 run should be *a result* feeding removal, not an in-place mutation. Diagnosis of the constraint as shipped: (a) paint had no direct authority — it was only ever SAM prompt material, so a mask could not exist without a GPU round-trip; (b) the track's version lineage (every SAM2 run already *was* a version) was invisible and unpinnable — removal implicitly consumed latest; (c) removal lived on the layer row, obscuring which mask version it consumed. **Design decision — promote the version surface, not the entity count:** splitting each SAM2 run into a separate track entity was rejected because the (video, layer) keying, the VOP-F11 restore protocol, the VOP-F14/F18 correction-session machinery, and the pending FileSet migration all assume one track per layer — and takes over versions already provide the coexistence the artist wanted (two propagations with different prompts as pinnable takes). Delivered: (1) **Mask row with takes** — one per version, labeled by production mode (`manual` / `SAM2` / `SAM2+corr` / `SAM2+paint`), pinned via a `selected` symlink on the track (the `latest` symlink stays the append pointer; new runs auto-pin, consistent with the F-take convention); serving, track info, and removal dispatch all resolve through the pinned version. (2) **Manual bake** — painted keyframes rasterize client-side (reusing the F13 alpha-carving rasterizer; the server normalizes alpha-carried rasters to the stored L-PNG convention) into a `manual` version with **hold-until-next-keyframe fill** (garbage-matte semantics, the Nuke/Resolve convention): the version stores only painted frames, expansion happens at read time (serve + removal dispatch), so one painted frame on a locked-off shot is a usable removal matte. (3) **Paint-over correction takes** — painted fixes composite over the pinned take's frames (the F14 client compositing, minus the re-propagation) into a new version with `correction` authorship on exactly the edited frames: the deterministic escape hatch for the VOP-F16 non-convergence loop. (4) **Remove relocated to the Mask row**, making "this removal consumes this take" structural. One paint surface throughout — the *operation* interprets it (Bake = verbatim authority, Propagate = SAM2 seed). Unit coverage added for hold-fill expansion, correction merge authorship, and pin-redirected reads (4 tests). U1-relevant consequence: the op DAG now has its three node ranks (paint → mask takes → result takes) visible as three nested row levels — the substrate Phase 3 chaining retargets over.

- **F3 — the surface goes op-centric: layers carry an explicit, artist-authored serial op stack, replacing hardcoded action buttons and implicit derived rows (August 8 2026).** Building on F2, the artist's next structural request: layers should be *op-centric* — appending a sub-layer operation from a menu (e.g. "Automask · SAM 2"), with op-specific parameters in the parameters window. Design decisions (each confirmed with the artist before implementation): (a) **hand-written per-op param panels** over schema-driven generic forms — full layout control now, schema rendering deferred until op count justifies it; (b) **op stack persisted on the CRDT layer with lineage rebuild** — run ops materialize durable outputs (mask-track versions / removal renders), so a restored layer's stack is reconstructed from lineage even when the doc predates op-centric layers or lost them (F11 churn); only appended-but-never-run ops are doc-only; (c) **full param migration** — SAM prompt-kind and staging-tier moved from panel-header globals into automask op params, removal tier/prompt/negative/seed from layer-level fields into remove op params (legacy fields remain as fallbacks for stack-less layers); the header keeps only view controls; (d) **"+ op" affordance on the layer row** over a creation-time prompt — paint-first stays frictionless. Structural rules carried from the A1 thesis: the stack is **linear and typed** (the + op menu is filtered by the stack tail — mask-source ops first, remove only after; no reordering UI, the type system is the ordering); **paint is material, not an op** (ops interpret it: Automask seeds SAM2, Manual mask bakes it verbatim); refinement gestures (Correct, paint-over bake) are actions on the automask op row, not stack entries. Incidental capability gained by the migration: the **eraser tier became artist-reachable** (the old `gen_mode` mapping could only express fast/quality; the op param is the full tier enum). One behavioural gate added: a layer whose stack lacks an automask op no longer fires SAM preview GPU calls on paint — a manual-masking layer never talks to SAM. Interaction-vocabulary note for U1: this generalizes the still-image surface's single `mask_op` field into a stack — the two surfaces now share the "layer carries operation intent" concept, with video adding depth.
  - **F3a — VOP-F14a recurs on the read path: the layer snapshot whitelist silently deleted the op stack on every read (August 8 2026).** First live test: + appended nothing, and a stale event reference crashed the panel. The event bug was mechanical (`e.currentTarget` read inside a queued state updater — React nulls it after the handler returns). The structural bug repeats VOP-F14a with a twist: the original lesson was "add new semantic fields at the schema/normalization boundary, not just the interactive sites" — and the *write* path was checked (`upsertLayer` stores wholesale, no normalization) — but the **read** path (`getSnapshot → normalizeAnnotationSnapshot → stableLayerRecord`) rebuilds every layer through a field whitelist, so `ops` was written intact and stripped on every read (and would have been dropped from persisted doc snapshots via `serializeAnnotationSnapshot`, which shares the whitelist). Sharpened lesson: a serialization boundary has *two* sides — audit read/serialize normalizers, not only write normalizers, when extending a persisted type. Fixed by admitting `ops` (deep-copied) into `stableLayerRecord`.

- **F4 — per-take provenance surfaced: every take now answers "what values made you" in the UI and API (August 9 2026).** Artist requirement following F2/F3: the parameter values an op ran with must be inspectable per version. Audit found the *recording* largely existed (removal takes carry a full `generation` recipe, reachable via the render-grid endpoint; mask-track versions carry propagation params; `OperationJob` holds complete dispatch state) but with three gaps: no UI surface, mask-take API summaries omitted params, and automask's `staging_tier`/`chain_source` were never folded into the version (only the job row). Closed: (a) segment ingest now records staging tier + chain source in the version's `propagation_params`; (b) `version_summaries()` returns a curated `params` record per take (model/tier/span/chain/fill policy/prompt-frame counts/correction lineage/latency/call id) — API-visible via the track info and track list endpoints; (c) the parameters panel renders a collapsible read-only **"Parameters used — take vN"** block under each op's editable params, fed by the pinned take (mask takes from the API summary; removal takes from the `generation` record, with a client-built interim recipe until reload for just-completed runs). Distinction the design keeps sharp: the op's *editable* params are "what the next run will use"; the take block is "what this take was made with" — same panel, adjacent, never conflated.

- **F5 — full-frame result stacking is winner-take-all and made "which result am I seeing" session-dependent; resolved by active-layer-driven single-result drawing. Depth-2 chaining verified end to end on real content (August 9 2026).** The 3.4 experiment ran on the real shot: Mask 2 (woman) → VOID remove → chained layer masks the man *on the result* → VOID remove with `chain_source` — the chained output is a clean empty bridge, both subjects gone, coordinates/frames intact (ffmpeg frame inspection of the ingested clip). **Closes Phase 3's exit criteria.** But the artist reported the chained erasure "not showing" at an in-span frame, and the diagnosis surfaced a viewport design flaw: removal results are *full-frame* clips, and the overlay drew every visible layer's result stacked — so only the last-ordered one was ever visible, the earlier ones pure wasted decode, and which one "won" depended on layer-order ties (session-dependent map iteration). Unlike still-image renders (regional, composable), video results don't stack meaningfully. Fix: draw exactly **one** result — the active layer's when eligible at the current frame, else the topmost eligible — with the badge naming whose result is shown (`RESULT · <layer> · hold C`). Verified live both ways: chained layer active → empty bridge; foreground_woman active → her eraser result. *Refined on artist feedback (same day): the initial fix kept a "topmost eligible" fallback when the active layer's result was hidden — which made the result-row eye appear non-local (hiding your result revealed another layer's). Fallback removed: ONLY the active layer's result ever draws; its eye toggles between that result and the original clip, verified live (eye off → original frame with mask tint, no leakage).* Secondary finding for U1/H3 from the same session: the chained take spans 600–796 (VOID's 197-frame cap clamped the 600–840 request server-side with only a log line), so frames 797–840 legitimately show mask-without-result — the span-cap needs client surfacing (recorded as follow-up alongside the slow-ingest phase label).

## Phase 3 — Chaining via derived-source layers (N8 + SPA, ~1 wk) — tests H5, U4

**Design revision (Aug 9 2026):** chaining surfaces as a **chained sub-layer**, not a second mask op inside one layer's stack. Rationale: paint strokes are keyed per layer, so two mask ops in one stack would make stroke ownership ambiguous (a Correct on automask #1 would consume strokes painted to seed automask #2; disambiguating would require per-stroke op tagging — mode state the F12 lesson argues against). A chained layer renders nested under the producing remove row (the artist-requested "SAM2 under a remove" reading), binds `layer.source = {layerId}`, and its whole stack operates on that layer's **pinned removal take**. Depth composes: a chained layer's remove output can itself be chained.

**The rebase contract (written before implementation, per VOP-F9):**

1. **Source space everywhere.** All artist-facing frame indices and pixel coordinates — prompts, spans, track frames, timeline markers, keyframes — are in the library clip's space (its timeline, its native pixel grid), at every API boundary, stored in every track version, regardless of chain depth.
2. **One rebase point: server-side staging.** A chained clip R (removal take) covers source frames `[R0, R1]` as file frames `[0, R1−R0]`. An op over source span `[a, b]` first clamps to `[max(a,R0), min(b,R1)]` (error if empty), then extracts file frames `[a−R0, b−R0]` from R's mp4. Every other span field (`job.inputs.span_start/end`, prompt rebase, ingest's `+span_start`, mask archive naming) stays source-based and untouched.
3. **Coordinates rebase for free.** The client always declares `source_size` = source native (W,H); the server rescales clicks/masks against the *measured* staged frame dims (the F9 contract) — which absorbs any chained-clip resolution difference (VOID's reduced-res takes included) with zero new code. Composited-native takes are 1:1.
4. **fps invariant.** Results are encoded at source fps; frame math is unchanged.
5. **Logged, always.** Every chained dispatch logs `CHAIN src=<layer>/v<run> offset=<R0> span src[a,b] → file[a−R0,b−R0]` — the diagnostic F9 says you'll want before you know you want it.
